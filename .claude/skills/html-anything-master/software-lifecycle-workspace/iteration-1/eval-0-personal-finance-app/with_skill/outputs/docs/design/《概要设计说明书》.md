# 概要设计说明书

## 1. 引言

### 1.1 编写目的

本文档基于《软件需求规格说明书》，对个人在线记账应用进行概要设计，定义系统整体架构、模块划分、数据设计和接口规范，为后续详细设计提供指导。

### 1.2 设计依据

- 《软件需求规格说明书》（Phase 2 产出）
- 《可行性研究报告》（Phase 1 产出）

### 1.3 设计目标与约束

| 约束 | 说明 |
|------|------|
| 技术栈 | 前端 React, 后端 Node.js (Express) |
| 通信协议 | HTTP/HTTPS, RESTful API |
| 数据格式 | JSON |
| 认证方式 | JWT (Bearer Token) |
| 部署方式 | 单机部署，Docker 可选 |
| 数据库 | SQLite（MVP），预留切换 PostgreSQL 的能力 |

## 2. 系统架构设计

### 2.1 整体架构风格

系统采用**前后端分离的分层架构**，前端为 React SPA，后端为 Express RESTful API 服务，数据库使用 SQLite。

架构层次：

```
┌─────────────────────────────────────────┐
│              浏览器 (Browser)             │
│         React SPA (axios + Router)       │
└─────────────────┬───────────────────────┘
                  │  HTTP/HTTPS (JSON)
┌─────────────────▼───────────────────────┐
│          Express API Server             │
│  ┌─────────────────────────────────┐    │
│  │       路由层 (Router Layer)      │    │
│  ├─────────────────────────────────┤    │
│  │     中间件层 (Middleware Layer)   │    │
│  │   auth, validation, error       │    │
│  ├─────────────────────────────────┤    │
│  │      控制器层 (Controller Layer)│    │
│  ├─────────────────────────────────┤    │
│  │        服务层 (Service Layer)    │    │
│  ├─────────────────────────────────┤    │
│  │      数据访问层 (Repository)     │    │
│  └─────────────────────────────────┘    │
└─────────────────┬───────────────────────┘
                  │  SQL
┌─────────────────▼───────────────────────┐
│             SQLite Database             │
└─────────────────────────────────────────┘
```

### 2.3 技术选型及理由

| 层级 | 技术 | 版本 | 理由 |
|------|------|------|------|
| 前端框架 | React | 18.x | 主流 UI 框架，生态完善，社区活跃 |
| 前端路由 | React Router | 6.x | React 官方推荐路由方案 |
| HTTP 客户端 | Axios | 1.x | 支持拦截器，便于统一处理认证和错误 |
| UI 组件库 | Ant Design | 5.x | 企业级 UI 库，内置表单、表格、图表组件 |
| 图表库 | Recharts | 2.x | React 原生图表库，轻量易用 |
| CSS 方案 | Ant Design 内置 + CSS Modules | - | 与 Ant Design 一致，降低引入成本 |
| 构建工具 | Vite | 5.x | 快速冷启动，优于 CRA |
| 后端框架 | Express.js | 4.x | Node.js 最流行的 Web 框架，成熟稳定 |
| ORM | Sequelize | 6.x | 支持 SQLite，API 直观，文档完善 |
| 密码加密 | bcryptjs | 2.x | 纯 JS 实现，无需编译 |
| 认证令牌 | jsonwebtoken | 9.x | JWT 标准实现 |
| 请求校验 | express-validator | 7.x | Express 中间件式参数校验 |
| 跨域 | cors | 2.x | Express CORS 中间件 |
| 数据库 | SQLite (via better-sqlite3 or Sequelize) | 3.x | 零配置、轻量、适合个人应用 |
| 运行时 | Node.js | 18+ | LTS 版本，稳定支持 |

## 4. 数据设计

### 4.1 数据库选型及理由

选用 **SQLite**，理由如下：
- 零配置，无需单独安装数据库服务
- 数据存储在单个文件中，便于备份和迁移
- 对于个人记账应用的数据量（单用户年记录量通常 < 1 万条），SQLite 性能完全足够
- 通过 Sequelize ORM 可在未来无缝切换至 PostgreSQL

### 4.3 核心数据表设计

#### User 表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 用户 ID |
| email | VARCHAR(255) | UNIQUE, NOT NULL | 邮箱（登录账号） |
| password_hash | VARCHAR(255) | NOT NULL | bcrypt 哈希后的密码 |
| nickname | VARCHAR(100) | DEFAULT '' | 用户昵称 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 注册时间 |
| updated_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 更新时间 |

#### Category 表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 分类 ID |
| name | VARCHAR(100) | NOT NULL | 分类名称 |
| type | VARCHAR(10) | NOT NULL, CHECK(type IN ('income','expense')) | 分类类型 |
| icon | VARCHAR(50) | DEFAULT '' | 图标标识 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |

#### Transaction 表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 记录 ID |
| user_id | INTEGER | FK, NOT NULL, INDEX | 所属用户 ID |
| category_id | INTEGER | FK, NOT NULL | 分类 ID |
| type | VARCHAR(10) | NOT NULL, CHECK(type IN ('income','expense')) | 类型 |
| amount | DECIMAL(10,2) | NOT NULL, CHECK(amount > 0) | 金额 |
| date | DATE | NOT NULL | 记账日期 |
| note | TEXT | DEFAULT '' | 备注 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 更新时间 |

## 5. 接口设计

### 5.1 外部 API 设计（REST 端点列表）

见第 3.3 节。

### 5.2 内部模块间通信方式

前端与后端通过 HTTP/HTTPS 的 RESTful API 进行通信，数据格式为 JSON。前端 Axios 实例配置统一的 baseURL 和请求拦截器（自动附加 JWT 令牌）、响应拦截器（统一错误处理，401 时跳转登录页）。

认证令牌通过 HTTP Header 传递：

```
Authorization: Bearer <JWT_TOKEN>
```

### 5.3 第三方服务集成

MVP 阶段不集成任何第三方服务。后续可考虑：
- 对象存储（用于用户头像上传）
- 邮件服务（用于密码重置）

## 7. 技术风险与应对

| 风险 | 应对措施 |
|------|---------|
| SQLite 并发写入锁 | 个人应用并发量极低，风险可控；使用 WAL 模式提升并发读性能 |
| 前后端分离的部署复杂度 | 使用 concurrently 统一启动，或后端托管前端静态文件 |
| JWT 令牌泄露 | 设置合理有效期（7 天），生产环境强制 HTTPS |
| 数据库备份 | 定期备份 SQLite 文件，提供数据导出功能 |
